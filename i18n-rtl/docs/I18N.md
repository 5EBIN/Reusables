# Interface languages

Acme ships its interface in six languages: English (`en`), Arabic (`ar`), Urdu (`ur`), Hindi (`hi`), Russian (`ru`) and Filipino (`fil`).
Arabic and Urdu are right-to-left (`RTL` in `frontend/lib/lang.ts`; the provider sets `lang` and `dir` on `<html>`).

> **Status: Urdu, Hindi, Russian and Filipino are MACHINE-DRAFTED and NEED NATIVE REVIEW before they are shown to customers.**
> Every file under `frontend/lib/i18n/{ur,hi,ru,fil}/` starts with a header saying so. English and Arabic are the reference languages (Arabic was
> written with the screens and the mockups). Do not launch a language to customers until its review checklist below is signed off.

## Where the strings live

| What | Where | Languages |
|---|---|---|
| Page text of the generated pages that is wrapped in `<T ar="...">English</T>` (the navigation titles) | key = the English text; Arabic is in the mockup (`data-ar`); `lib/dictionary.ts` reads `lib/i18n/<lang>/misc.ts` (`T`) | ar, ur, hi, ru, fil |
| Message tables (sentences with `{placeholders}`): `lib/messages.ts` (+ `messages-workspace.ts`), `lib/msg-d.ts`, `lib/messages-e.ts`, `lib/messages-reports.ts`, `lib/authoring-messages.ts`, `components/distribute/strings.ts`, `lib/runner/strings.ts`, `components/interview/strings.ts` | English + Arabic next to the screen; the other four in `lib/i18n/<lang>/` | all |
| Loader sentences (view-models are language-agnostic) | `enc("key", args...)` in `lib/decode.ts`; the client translates with `useDecode()`; arguments may themselves be messages (relative times) | all |
| Relative times and dates | `relTimeEnc`, `dayMonthEnc` (`lib/format.ts`), `whenLabelEnc`, `shortDateEnc` (`lib/people.ts`) for decoded pages; `relTimeL`, `dayMonthL` for client components that know the language | all |

`lib/i18n/registry.ts` (`tableFor`) is the one lookup used by every table; `lib/i18n/catalog.ts` lists the English and Arabic source of every table (used by
tests and by the export script). Lookup order for a key: Arabic -> the Arabic table; Urdu/Hindi/Russian/Filipino -> `lib/i18n/<lang>/`; anything missing -> English.
An unknown language is English. A key is never shown to a user.

### Why the six message tables were not folded into one module

Done on purpose, not forgotten: 13 keys exist in more than one table with different wording (`network`, `required`, `forbidden`, `saved`, `load_failed`,
`not_found`, `no_survey`, `saving`, `preview`, `upload`, `privacy`, `expired`, `copied`), each table has its own formatter/hook signature
(`useMsg`, `useMsgD`, `useRMsg`, `useAMsg`, `useDMsg`, `rt`, `P`) used by ~60 call sites, and `lib/decode.ts` only resolves `lib/messages.ts` keys. A flat merge would
either change what users read or need every call site rewritten. Instead the registry/catalog above gives the single coherent view (one lookup, one
export, one completeness test) while each table keeps its own namespace. If a future change renames the colliding keys, the tables can be merged mechanically.

## Rules for translators

- Translate the *value*. Never change a key, a `{placeholder}` (`{n}`, `{0}`, `{s}`, `{cond}` ...) or a `%`/markup character. Placeholders may move to fit grammar.
- Keep product terms stable: Acme, SLA, NPS, CSAT, CX, SSO, SMS, WhatsApp, QR, CSV, JSON, PDF, TXT, DNS, GST stay in Latin script.
- Respondent-facing strings (`runner`, `interview` tables) must be polite and plain; the rest follows a neutral business register.
- Russian counts are written as "Label: {0}" where plural agreement would otherwise be needed (1 / 2-4 / 5+).
- Urdu must read naturally in Nastaliq conventions (Urdu vocabulary, not Arabic loanwords where Urdu has a common word); numbers stay in Western digits in the interface.

## How to export the strings for a translator

From `frontend/`:

```
npx vite-node -c vitest.config.ts scripts/i18n-export.ts > strings.json                 # JSON array of {table, key, english, arabic, ur, hi, ru, fil}
I18N_FORMAT=csv npx vite-node -c vitest.config.ts scripts/i18n-export.ts > strings.csv   # same as CSV (opens in any spreadsheet)
```

Table `t` is the page text (key = the English text); the others are message tables. To import a reviewed language, edit the matching file under
`frontend/lib/i18n/<lang>/` (`messages-1/2.ts`, `d.ts`, `e-reports.ts`, `authoring-1/2.ts`, `distribute-1/2.ts`, `respondent.ts`, `misc.ts`). The tests below fail if a
key is missing, empty, stale or loses a placeholder.

## Review checklist (per language; one reviewer who is a native speaker and has used the product)

1. Read the exported CSV top to bottom against the English column. Fix meaning errors first, tone second.
2. Placeholders: every `{x}` is present and in a place that reads correctly (`tests/i18n.test.tsx` checks presence, not grammar).
3. Screens, in the language, at phone width and desktop: navigation titles, auth, overview, approvals, team, templates, builder (design/settings/logic), distribute (test send), kiosk, runner, interview.
4. Buttons: is the verb clear, and short enough not to wrap badly? Is "Approve" distinguishable from "Accept"/"Agree" (legal meaning)?
5. Legal and consent text (`consent_*`, `site_consent`, `agree`, `thanks_b`, `withdrawn*`): have the legal reviewer confirm the wording, not only the translator.
6. Errors: no blame, say what to do next.
7. Right-to-left (Arabic, Urdu): numbers, `{placeholders}` with Latin text, punctuation and parentheses render in the right order; icons that imply direction (arrows) mirror.
8. Dates and times: month names and the order "12 Sep" / "Today 10:00" read naturally (`mon_1..12`, `date_dm`, `when_*`, `rel_*`).
9. Sign-off: record reviewer, date and the commit in the table below, then remove the machine-drafted header from that language's files.

| Language | Reviewer | Date | Commit | Status |
|---|---|---|---|---|
| ur | - | - | - | machine-drafted |
| hi | - | - | - | machine-drafted |
| ru | - | - | - | machine-drafted |
| fil | - | - | - | machine-drafted |

## Tests

- `frontend/tests/i18n.test.tsx`: every `<T>` page leaf and every key of every message table exists in ur/hi/ru/fil, no value is empty, no stale keys, placeholders preserved;
  lookups fall back to English; Urdu is RTL (`dir="rtl"`, `lang="ur"` on the document) and Hindi/Russian/Filipino are LTR; `<T>` renders each language.
- `frontend/tests/arabic-coverage.test.tsx`: relative times, month names, "Today 10:00" labels and nested messages in Arabic (and Urdu, Russian, fallbacks).

## Known gaps (honest list)

- Only the elements the mockups mark with `data-ar` are wrapped in `<T>`; all other static text of the generated pages stays English in every language (the 1:1 fidelity rule
  forbids rewriting them). Wired interactive parts (messages) are fully translated.
- Loaders whose pages do not decode view-model text still build English sentences: `lib/loaders/surveys.ts` ("N questions", "Live/Draft/Closed", relative times), `lib/loaders/billing.ts`
  ("Billed annually - renews ..."), `lib/views/security.ts`, `lib/views/kiosk.ts` ("1 min ago", "Never"), `lib/views/dashboards.ts`, `lib/views/market-research.ts`, `lib/views/panels.ts`,
  `lib/views/orgintel*.ts`, `lib/views/engagement.ts`, `lib/views/f360.ts`, `lib/exports-view.ts`. Making them translatable means adding `textWrap: "m"` to the page's wiring, emitting `enc(...)` in the loader
  and updating that page's tests; the helpers above (`relTimeEnc`, `dayMonthEnc`, `whenLabelEnc`, `shortDateEnc`) are ready for it.
- Numbers are always Western digits in the interface (the runner has its own Arabic-Indic / Extended Arabic-Indic digit option for respondents).
